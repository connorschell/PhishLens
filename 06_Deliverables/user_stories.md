# User Stories with Acceptance Criteria

**PhishLens — explainable AI-assisted phishing detection for the Gmail web client**
Connor Schell · CYBR 498W · Dr. Mohammad Almalag · Deliverable #4 · drafted for IM1

Stories follow the course format: *as \<user type\>, I need the system to
\<task\> for \<reason\>*. They are organized by the stakeholder performing them
(`06_Deliverables/stakeholders.md`). Each story carries acceptance criteria and
the WBS item that implements it.

**Status key:** ✅ built and tested · 🔨 in progress · ⬜ not yet built

---

## Message Recipient

### US-01 — See a verdict on the open message ✅ (WBS 3.3, 4.2, 4.3)

As a message recipient, I need the system to score the message I am currently
reading and show me a risk score and severity tier, so that I know whether to
treat it with suspicion before I act on it.

**Acceptance criteria**

- The panel appears for the message currently open, and updates when a different
  message is opened.
- The verdict carries a 0–100 risk score and exactly one of four tiers:
  `clear`, `caution`, `suspicious`, `dangerous`.
- The verdict is never a bare binary — "phishing / not phishing" is not an
  acceptable rendering of a tier.
- The scan completes fast enough that the panel is populated before the user has
  finished reading the message header. Measured budget: < 500 ms round trip
  (83 ms scoring locally).

### US-02 — Understand *why*, in plain language ✅ (WBS 2.3)

As a message recipient, I need the system to list the specific signals that
produced the score in language I can read without security training, so that I
can judge the verdict myself instead of taking it on faith.

**Acceptance criteria**

- Signals are returned as a ranked list, highest contribution first.
- Every sentence is a format string over a measured value. No sentence is
  generated by a language model; nothing in the scoring path calls an LLM.
- A signal that has nothing to say about this message is silent rather than
  padded with a default sentence.
- Each signal names what was observed, not just a feature name — "the link text
  shows one domain and points at another" rather than `display_url_mismatch`.
- Model-layer and rule-layer signals are distinguishable in the response
  (`kind: model | rule`).

### US-03 — See what argues *for* the message ✅ (WBS 2.3)

As a message recipient, I need the system to show me the mitigating factors as
well as the incriminating ones, so that a `caution` tier reads as a judgment
rather than an accusation.

**Acceptance criteria**

- The response carries a `mitigating` list separate from `signals`.
- A message scored `clear` still returns an explanation; the panel is never
  empty.

### US-04 — Disagree with a verdict ⬜ (WBS 3.4, 4.4)

As a message recipient, I need the system to let me report that a verdict is
wrong, so that a message wrongly flagged as dangerous — or missed entirely — is
visible to whoever maintains the model.

**Acceptance criteria**

- The control distinguishes a false positive from a false negative.
- An optional note is accepted, bounded at 500 characters.
- One report per install per scan; a second submission updates rather than
  duplicating.
- Submitting feedback does **not** change the verdict shown, now or on re-scan.
  Feedback is review input, never applied automatically.
- The control confirms receipt without requiring the user to leave Gmail.

### US-05 — Have the message not be stored ✅ (WBS 3.1)

As a message recipient, I need the system to score my mail without retaining it,
so that using a phishing detector does not create a copy of my inbox somewhere
else.

**Acceptance criteria**

- No table has a column capable of holding a subject, body or sender address.
- Re-scanning the same message is recognizable via a salted `message_fingerprint`
  that cannot be reversed to the message.
- The first-run screen states in one sentence that the open message is sent for
  scoring and is not stored (WBS 4.1).
- A database disclosure yields measurements and scores, not anyone's mail.

### US-06 — Still get a verdict when the database is down ✅ (WBS 3.3)

As a message recipient, I need the system to tell me whether the message is
dangerous even when its own storage is unavailable, so that an infrastructure
problem does not silently leave me unprotected.

**Acceptance criteria**

- `/scan` returns the full verdict and explanation with `persisted: false` and
  `scan_id: null` when the database is unreachable.
- Persistence failure never produces an error response or an empty panel.
- Features that depend on a stored scan (feedback) degrade visibly rather than
  failing silently.

### US-07 — Not be misled when a reputation lookup is unavailable ⬜ (WBS 3.5)

As a message recipient, I need the system to leave the URL-reputation signal out
when Safe Browsing cannot be reached, so that an unavailable third party is not
reported to me as evidence of safety.

**Acceptance criteria**

- A missing or expired `url_reputation` row causes the signal to be unused, not
  defaulted to "safe".
- No explanation sentence claims a link was checked when it was not.
- Scan latency does not degrade past the US-01 budget when the lookup times out.

## Dashboard Reviewer

### US-08 — Review scan history ⬜ (WBS 4.5)

As a dashboard reviewer, I need the system to show me recent scans with their
score, tier and model version, so that I can see how the system is behaving
across many messages rather than one at a time.

**Acceptance criteria**

- Scans are listed newest first, filterable by severity.
- Every row shows which model version produced it.
- The stored explanation is viewable as it was shown to the user, not recomputed
  from the current model.

### US-09 — Work the feedback queue ⬜ (WBS 4.5)

As a dashboard reviewer, I need the system to show me unreviewed disagreements
and let me mark them triaged, so that user reports are worked once rather than
repeatedly reconsidered.

**Acceptance criteria**

- Default view is feedback where `reviewed_at IS NULL`, oldest first.
- Marking reviewed is recorded with a timestamp and does not delete the report.
- Each report links to the scan's stored measurements and explanation.

### US-10 — Read performance metrics ⬜ (WBS 4.5)

As a dashboard reviewer, I need the system to report precision, recall and
false-positive rate for the active model, so that I can judge the system on the
metrics that matter for phishing rather than on accuracy.

**Acceptance criteria**

- Accuracy is not displayed as a headline metric anywhere in the dashboard.
- Metrics are attributed to a specific model version and training date.
- Full and ablated figures are both reachable.

## Model Maintainer

### US-11 — Train and evaluate a model ✅ (WBS 2.1)

As a model maintainer, I need the system to train a classifier and report
precision, recall and false-positive rate on a held-out set, so that I can tell
whether a change improved detection or only moved errors around.

**Acceptance criteria**

- The train/test split is campaign-aware; a leakage check refuses to write on
  detection. Measured leakage 0%.
- Metrics are emitted for both the full and ablated feature sets.
- Evaluation output is written to a file, not only printed.

### US-12 — Know which features produced a score ✅ (WBS 2.2)

As a model maintainer, I need the system to expose per-feature contributions
from the trained model, so that the explanation the user reads is derived from
what the model actually did rather than from a plausible story about it.

**Acceptance criteria**

- Contributions come from the trained model, not a post-hoc approximation.
- Ranking is by share of the decision, not by raw model weight.
- An API response for a message equals a direct call to the model, field for
  field — asserted by test, so there is no second implementation to drift.

### US-13 — Promote a model reversibly ⬜ (WBS 2.4 / ops)

As a model maintainer, I need the system to record each model version with its
severity thresholds and let exactly one be active, so that a promotion can be
undone and past verdicts stay attributable.

**Acceptance criteria**

- A unique index enforces one active model.
- Severity thresholds are stored with the version, so changing a tier boundary
  produces a new version rather than an in-place edit.
- Existing scans keep pointing at the version that produced them.

### US-14 — Calibrate against legitimate bulk mail ⬜ (WBS 2.4)

As a model maintainer, I need the system to be evaluated against legitimate
marketing and transactional mail specifically, so that the senders most likely
to be wrongly flagged are measured rather than assumed.

**Acceptance criteria**

- A held-out set of legitimate bulk mail is scored and its tier distribution
  reported.
- False-positive rate is reported for that slice separately from the overall
  figure.
- Threshold changes made as a result are recorded in the Change Log.

## Evaluator

### US-15 — Install and run the system unaided ⬜ (WBS 5.5)

As the evaluator, I need the system to come with instructions that work against
the live instance and against a fresh host, so that I can verify the project
without the author present.

**Acceptance criteria**

- README covers both paths: using the hosted URL, and standing the stack up from
  scratch.
- The packaged extension loads in Chrome from the provided archive.
- The live URL serves over HTTPS with a valid certificate.

### US-16 — Reproduce the reported numbers ⬜ (WBS 5.5)

As the evaluator, I need the system to let me regenerate the evaluation output
from the repository, so that the metrics in the final report are checkable
rather than asserted.

**Acceptance criteria**

- Documented commands regenerate the dataset, model and metrics files.
- Regenerated figures match the report, or the difference is explained.

## Cross-cutting: the installation as a client

### US-17 — Register without shipping a secret ⬜ (WBS 3.4)

As a message recipient, I need the extension to obtain its own credential at
first run rather than carrying one in its source, so that the credential can be
rate-limited and revoked for my install alone.

**Acceptance criteria**

- `POST /register` issues a 32-byte CSPRNG token, returned once.
- Only a SHA-256 hash is stored; a database disclosure yields no usable token.
- The token lives in `chrome.storage.local`, not readable by Gmail's page
  scripts.
- Revoking one install does not affect any other install.
- The design does not claim to authenticate a *person* — the token identifies an
  installation.

### US-18 — Be protected from a hostile client ⬜ (WBS 3.4)

As the system operator, I need the API to bound and validate every inbound
field, so that a client the server does not control cannot exhaust it.

**Acceptance criteria**

- Every request field has a maximum length; oversized payloads are rejected
  before scoring.
- Per-install rate limiting on `/scan`; per-IP rate limiting on `/register`.
- Rejections are explicit status codes, not silent truncation.
